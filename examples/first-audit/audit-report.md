# 审查报告：从“降低 40%”到可验证的 15.79%

**结论：原方案不可行，原收益与最优性表述不能采用。**

这是人工设计错误后运行代码核验的教学演示。本文是本次整理的参考报告，不是独立用户反馈，也不是对技能检出率的盲测。

| 问题 | 证据位置 | 核验结果 | 修复 |
|---|---|---|---|
| 容量约束违反 | `problem.md`、`solver-before.py` 的 `solve()` | A 最多发 6 件，代码发 8 件 | 在可行域内重新求解 |
| 论文与代码成本不一致 | `paper-before.md` 的“总成本” | 8×2+2×5=26，论文写 24 | 统一从求解结果提取成本 |
| 降本比例错误 | `paper-before.md` 的“降低 40%” | 基线成本 38；即便忽略不可行性，26 相对 38 的降幅也只有 31.58% | 用修复方案计算：32 相对 38 降低 15.79% |
| 最优性缺乏依据 | `paper-before.md` 的“全局最优” | 原代码只返回一个固定方案，没有最优性证明 | 枚举全部 7 个可行方案，并提供单调性证明 |

## 如何复核

在仓库根目录运行：

```bash
python3 examples/first-audit/verify.py
```

脚本实际调用原程序，再独立枚举可行方案。标准输出应与 `expected-results.json` 一致。
只使用 Python 标准库，不联网、不修改输入、不安装依赖。

修订稿见 [paper-after.md](paper-after.md)。它同步修改了方案、成本、收益比例与最优性依据。

## 这份演示能说明什么

它展示了可行性、结果一致性、收益计算和最优性依据四类检查如何落到可复核证据上。它不证明技能能在所有实际论文中自动找到同类问题，也不构成竞赛获奖能力验证。
